### [OpenAI 预印本声称证明 ETH 为假](https://github.com/openai/math/blob/main/preprints/The-Exponential-Time-Hypothesis-is-False-October-25-2026/paper.pdf) ⭐️ 8.0/10

OpenAI 的数学预印本仓库发布论文，声称证明了指数时间假设（ETH）为假；ETH 通常指 3SAT 等问题无法在 2^\{o\(n\)\} 时间内求解。这是一项尚未经同行评审或独立验证的预印本主张，目前只能视为作者提交的证明，而非已确认的复杂度理论结论。论文同时指出，2^\{o\(n\)\} 形式的时间下界不会在一般多项式时间归约下传递，因此该结果并不推出一般 NP 问题具有次指数时间算法。

hackernews · vok · 10月26日 21:59 · [社区讨论](https://news.ycombinator.com/item?id=50251661)

**「背景」** 指数时间假设（ETH）是计算复杂性理论中的一条具体假设，通常表述为：一般 3-SAT 不存在运行时间为 2^\{o\(n\)\} 的算法，其中 n 是变量数。它比 P≠NP 更强，用来排除 SAT 及许多相关问题获得次指数级加速的可能。

**「实际影响有限，且尚待验证」** 对算法实践者而言，即便该结论成立，也不会立刻带来更快的 SAT 求解器：评论者引用论文原文指出，形如 2^o\(n\) 的运行时间界无法通过一般的多项式时间归约传递，因此并不能推出一般 NP 问题存在亚指数时间算法，最坏情况复杂度与实用 SAT 求解之间仍隔着一层。OpenAI 方面表示正与学术社区合作理解和解释这一关于 ETH 的结果，说明该工作目前仍属需要外部核验的预印本声明，而非已被独立确认的定论。

**「社区讨论」** 有评论者认为，若证明成立，其分量与 P=NP 处于同一量级但不等同，并追问该方法是否有实际 SAT 求解应用，以及依赖 SETH 的结论（如自注意力二次复杂度）会受到何种影响。也有评论者提醒，这不等于 NP 具备次指数算法，因为 2^\{o\(n\)\} 下界不按一般多项式归约传递。

### [微软 Pylance 仓库记录 Python 类型服务器协议](https://github.com/microsoft/pylance-release/blob/main/docs/tsp/type-server-protocol.md) ⭐️ 7.0/10

微软 Pylance 仓库中的文档描述了 Type Server Protocol（TSP），目标是规范 Python 类型检查器与编辑器、IDE 工具之间的集成。现有材料没有给出协议版本、发布时间或已完成的兼容实现，因此应将其视为规范文档，而不是已经发布的产品能力。社区讨论主要围绕它为何不能仅靠 LSP 完成、相较其他带类型的 JSON-RPC 方案有何优势，以及为何一个仅面向 Python 的协议使用通用命名。

hackernews · adamnemecek · 10月26日 18:14 · [社区讨论](https://news.ycombinator.com/item?id=50248371)

**「背景」** Type Server Protocol（TSP）是一个 JSON-RPC 协议，它复用与 LSP 相同的传输层，但把类型服务器维护的工作区类型分析状态——协议版本、快照、Python 搜索路径、导入解析以及计算得到的类型查询结果——直接暴露给外部客户端。这一层之所以存在，是因为 LSP 本身面向编辑器功能，并不提供对这类类型数据的结构化访问。协议源码注释同时说明它“目前专用于 Python，未来可能泛化”，这与社区对其占用通用协议命名空间的质疑直接相关。

**「影响」** 对类型检查器开发者而言，TSP 的作用取决于它能否被 Pylance 之外的实现采用：社区讨论称 Astral 的 ty 将会支持该协议，而 ty 是用 Rust 编写、同时提供类型检查和语言服务器功能，并且官方支持 Python 3.10 及以上版本的工具。若这一支持落地，使用 ty 的团队才可能在非 VS Code 编辑器中复用同类的类型查询接口；目前这仍只是讨论中的采用计划，微软的协议文档并未确认已有第三方实现。

**「社区讨论」** basedpyright 维护者曾公开批评该协议，而有评论称 Astral 的 Ty 计划支持 TSP；这些说法来自社区，未在本次材料中得到独立验证。另有评论者质疑其命名占用了通用协议命名空间，并询问它相对 LSP、tRPC 等方案的具体收益。

### [webframe：用系统无头 webview 执行网页的 Go 小工具](https://simonwillison.net/2026/Oct/26/webframe-evaluation/) ⭐️ 7.0/10

Jeff Lindsay 的 webframe 是一个用 Go 编写的小工具：给它一个 URL 或文件，它会在隐藏的无头 webview 中执行该页面，把 console.log\(\) 输出到标准输出、把异常输出到标准错误。它基于 glaze 库调用系统浏览器（macOS 上的 WKWebView、Linux 上的 WebKitGTK、Windows 上的 WebView2），因此既不捆绑自己的浏览器引擎，也不依赖 Playwright。Simon Willison 让 Claude Opus 5.5 对它做了测试并撰写研究报告，分别按 shot-scraper 的 JavaScript 用法评估其抓取网页的能力、并将其作为沙箱工具考察；不过所给摘录只包含报告链接和测试提示词，没有给出具体评估结论。

**「背景」** webframe 不打包自己的浏览器引擎，而是通过 glaze 库调用操作系统自带的 WebView（macOS 上是 WKWebView、Linux 上是 WebKitGTK、Windows 上是 WebView2）来执行页面。传统基于 Playwright 的抓取工具需要随附完整的浏览器二进制，这正是 webframe 体积更小、但能力也受制于系统 WebView 的原因。作者 Simon Willison 将其与自己 shot-scraper 项目中的 \`javascript\` 子命令相比较，后者沿用同样的“把网页当程序跑并读取脚本输出”的模式。

**「影响」** 对开发者来说，webframe 的价值在于体积小且无需 Playwright；代价是实际运行依赖目标机器上已安装的系统 webview 组件（WKWebView、WebKitGTK 或 WebView2），跨平台部署时不能指望随工具附带浏览器引擎。若考虑用它替代现有的 shot-scraper/Playwright 抓取流程，需要先针对具体平台和目标站点验证行为。
